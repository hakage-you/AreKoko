## 0. この文書について

### 0.1 目的

設計と詳細設計から、**「何が確かめられれば、設計どおりに動いていると言えるか」** を要求として並べ、それぞれをどの試験で確かめているかを示す。試験の抜けを見つけ、次に足す試験を決める土台にする。

| 文書 | 答える問い |
|---|---|
| 設計・詳細設計 | 何を作るか |
| **この文書** | **何を確かめるか**（要求と、試験との対応） |
| 結合試験の観点（`integration-test-plan.md`）と `tests/` | どう確かめるか |

### 0.2 書き方

- 要求は「〜こと」の形で、外から見て確かめられるように書く。
- 1つの要求に、根拠（設計の節）と、確かめている試験を対応づける。
- 要求の ID は `TR-<区分>-<番号>`。番号は増やすだけで、振り直さない（消した要求は欠番にする）。

### 0.3 凡例

**重**（重要度）：

| 記号 | 意味 |
|---|---|
| 高 | 外れると、データを失う・壊す・黙って変わる（設計 原則1・2・7、保存） |
| 中 | 外れると、操作が規則どおりに動かない |
| 低 | 外れると、見た目・案内・使い勝手が悪くなる |

**状**（状態）：

| 記号 | 意味 |
|---|---|
| ○ | 自動の試験で確かめている |
| △ | 一部だけ確かめている（ランダム検査の一般的な確認だけ、場合の一部だけ、など）。足りない部分は「試験」の欄に書く |
| 手 | 画面で確かめた記録がある（`integration-test-plan.md` 7章・段階6・段階7） |
| × | 試験も記録もない |

**試験**の欄の書き方：

| 書き方 | 意味 |
|---|---|
| 単 `core/load`「…」 | 単体試験 `tests/core/load.test.ts` の、名前に「…」を含む試験 |
| 結 S1、U3 など | 結合試験。番号は `integration-test-plan.md` の観点番号（試験の名前の先頭にも付いている） |
| SC-01 など | シナリオの試験（`docs/scenarios.md`）。E2E（`e2e/`）と結合（`tests/integration/scenarios.test.ts`）の両方 |
| ランダム `property/ops` | ランダム検査 `tests/property/ops.property.test.ts` |
| 画面 | ブラウザで手で確かめる |

## 1. 試験の水準と共通の約束

### 1.1 水準

| 水準 | 置き場所 | 対象 | 道具 |
|---|---|---|---|
| 単体 | `tests/core`・`geometry`・`editor`・`search`・`file`・`view`・`app` | 関数・クラス1つ | Vitest |
| 結合 | `tests/integration` | `AppStore`＋`DocumentSession`＋中核＋検索。利用者の操作の流れを公開の操作だけで再現する | Vitest、偽の保存先・偽の時計 |
| ランダム | `tests/property` | 操作の列、ランダムに壊した文書 | fast-check |
| E2E | `e2e/`（`npm run test:e2e`） | シナリオを本物の画面から通す（`docs/scenarios.md`） | Playwright（開発用の `?memory`） |
| 画面 | ブラウザ（開発用の `?memory`） | Svelte の画面、ブラウザの API とのつなぎ | 手で操作。記録は `integration-test-plan.md` |

単体・結合・ランダムの試験は Node で動く（`vite.config.ts` の `environment: 'node'`）。画面（`src/ui/`）は、主要な流れ（シナリオ）だけを E2E で確かめる（設計 14章「画面のテストは主要な流れに絞る」。詳細設計(シナリオ)）。

### 1.2 共通の約束

- 操作に渡す文書は deep freeze する（入力を書き換えないことを、すべての操作の試験で確かめる）。
- ID と時刻は、差し込んだ決定的な生成器を使う（結果が毎回同じになる）。
- 結合試験は、毎回次を確かめる（`expectHealthy`）：
  - 保存されたファイルを `analyzeDocument` にかけると `ok`（修復が要らない）。
  - 保存されたファイルは改行・空白なし。
  - 画面の状態の文書が `validateDocument` を通る。
  - 「保存済み」と出ているとき、画面の文書とファイルの中身が一致する。

- 重要度「高」の要求は、状態が ○ か 手 であること（2026-10-09 の時点で × と △ が残っている。17.1）。
- 画面の確認（手）は、段階の区切りと画面の大きな変更のたびに行い、`integration-test-plan.md` に記録する。
- 設計を変えたら、この文書の要求も同じ変更で直す（要求を消すときは欠番にする）。
