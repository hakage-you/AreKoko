# テスト要求仕様書（TRS）の書き方

このフォルダの TRS は、実装から独立した「正しさの判定基準」である。利用者（ユーザー）が読んで確かめられる言葉で書く。試験はここから作り、試験が落ちたときはここと設計に照らして判断する。

領域ごとに1つのファイルにする（今は `kuukan-editor.md`＝クウカン編集だけ）。書き方の決まりはこのファイルにまとめ、領域のファイルには繰り返さない。

## 1. 書くもの・書かないもの

- **書く**：利用者から見える約束だけ。利用者が何をしたら、画面に何が見え、文書（保存される中身）がどうなるか。文書は利用者の言葉で書く（「モノ『ペン』の置き場は『棚1』になる」）。
- **書かない**：
  - 関数の約束、エラーのコード、内部の計算、データの欄の名前（`membership.areas` など）、ID の形式
  - 「押せる幅 12px」のような実装のルール
  - どう確かめるか（結合か E2E か、など）。これは試験計画（`docs/integration-test-plan.md`）に書く

## 2. 出典の書き方

どの項目にも、根拠になる設計の節を付ける。リポジトリの文書を次の略し方で直接指す。

| 略し方 | 文書 |
|---|---|
| 設計 | `docs/design.md` |
| 詳細 | `docs/detailed-design.md`（段階1〜2：中核・幾何） |
| 詳細(UI) | `docs/detailed-design-ui.md`（段階3〜4：ファイル操作・リスト） |
| 詳細(編集) | `docs/detailed-design-editor.md`（段階5：クウカン編集） |
| 詳細(ビュー) | `docs/detailed-design-view.md`（段階6：クウカンビュー） |
| 詳細(仕上げ) | `docs/detailed-design-finish.md`（段階7） |
| レビュー1 | `docs/detailed-design-review1.md` |
| 付録A | その TRS の付録A（ユーザーが決めたこと） |

書き方の例：「設計 7.2」「詳細 9.6」「詳細(編集) 4」「詳細(編集) 0（E1）」「レビュー1 R-B7」「付録A A-05」。

## 3. 文言と置き場所の印

画面の文言そのものは、ふつう約束しない。約束するのは、画面を見て利用者が何を知ることができるか（伝わる中身）。文言は画面の設計の側で決め、試験では操作の手がかりとして使う。

- **「」**：約束の文言。画面の文言がこれと違えば不具合。次のときだけ使い、根拠を付ける。
  - 設計（または付録A）が文言を決めているとき（例：レビュー1 R-B7「左右に分ける」、付録A A-11「名前なし」）
  - 用語集（設計 4章）の言葉（「クウカン」「未設定」「下書き」など）
  - 設計の規則で決まる値（「床1」「〇〇のコピー」、利用者が入れた名前など）
- **〈〉**：操作の手がかり。設計が文言を決めていないボタン・メニュー・タブ・ダイアログの名前。試験では、画面の上で同じ働きをするものの名前に読み替えてよい。
- **伝わる中身**：文言が決まっていない表示は、何が分かればよいかで書く（例：「確認で、どこから何件がどこへ移るかが分かる」）。
- **置き場所・見た目**（どの欄・どの列・どの順・色・形）は、設計が決めているときだけ判定に書き、根拠を付ける。決めていないときは書かない。

## 4. 項目の書き方

```
#### ED-018 仕切りを入れてエリアを2つに分ける
- 根拠：設計 7.2、詳細(編集) 8.3
- 前提：P-03（確定したクウカン）／下書きなら P-05
- 操作：…
- 判定：
  - ① …
  - ② …
- 境目の場合：
  - ③ …
- 重要度：高 — …
```

- **前提**は「前提の文書」（各 TRS の節。P-01 など）を名前で指し、項目ごとに書き下さない。下書きか確定したクウカンかを必ず書く。両方で確かめるときは、場合を分けて判定を書く。
- **判定**は1つの文に1つの見て分かること。文ごとに丸数字を振り、試験からは「ED-018-②」のように指す。
- だれが見ても同じに決まるように書く。「など」「等」「または」「目立つ」のような言葉は使わない。操作が2通りあるときは、両方を確かめるのか、どちらか一方なのかを書く。
- **共通の判定**（各 TRS の節。K-1 など）は、当てはまるすべての項目に効く。項目ごとに繰り返さない。
- 設計で決まっていないことは推測で埋めない。「あいまいな点」に挙げてユーザーに決めてもらい、決まったら付録Aに足し、同じ変更で設計書にも書き戻す。

## 5. 重要度

| 重要度 | 意味 |
|---|---|
| 高 | 外れると、データを失う・壊す・黙って変わる（設計 原則1・2・7、保存） |
| 中 | 外れると、操作が規則どおりに動かない |
| 低 | 外れると、見た目・案内・使い勝手が悪くなる |

同じ害なら同じ重要度にする。

## 6. 番号の決まり

- 項目の番号（ED-001 など）は増やすだけで、振り直さない。消した番号は欠番にし、変更履歴に書く。
- 判定の丸数字も、項目の中で振り直さない。消したら欠番にする。

## 7. 更新の流れ

- 各 TRS の見出しに、元にした設計の版（コミット）を書く。
- 設計を変えたら、同じ変更で TRS と試験も直す（設計 → TRS → 試験）。
- 利用者から見える振る舞いを変える実装は、同じコミットで設計に書く。設計にない振る舞いは、TRS から確かめようがない。
- TRS を直したら、各 TRS の変更履歴に1行書く。

## 8. 試験が落ちたとき

次の3つのどれかに分ける。試験を実装に合わせて直すことはしない（試験の操作の誤りを直すのは別）。

| 分け方 | すること |
|---|---|
| 不具合 | 実装を直す。直すまで、試験は落ちたままにする |
| 設計の抜け | ユーザーに決めてもらい、設計 → TRS → 試験の順に直す |
| TRS の誤り | 設計の文を根拠に TRS を直す。実装を根拠にしない |

## 9. 旧 TRS との関係

`docs/test-requirements.md`（TR-*）は、利用者から見える約束と実装の約束が混ざった古い一覧。領域ごとにこのフォルダの TRS ができたら、その領域の TR-* の項目は、こちらの項目番号との対応を付けて外す。実装の約束（修復の規則・不変条件・往復・幾何の境目など）の置き場所は、ほかの領域へ広げる前に決める。
